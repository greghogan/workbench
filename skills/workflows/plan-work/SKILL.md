# Collaborative planning

Read the applicable decisions and inspect the affected system before asking questions the repository can answer. Use the
developer's chosen planning method and existing document conventions. Reuse the requested plan and related records; do
not invent a record type or impose a specification framework. A plan describes future work; a task can aggregate
coherent work across several commits. Keep substantive context searchable in files.

Develop the intended outcome, scope, constraints, acceptance criteria, approach, dependencies, and verification to the
depth the work needs. Keep alternatives and unresolved choices visible. These are useful contents, not mandatory
sections or a fixed sequence. Link authoritative requirements rather than copying them into competing specifications.
Separate a human-reviewable overview of why, what, and how from proportionate implementing-agent detail; use visuals
where they help understanding.

Distinguish planning acceptance, readiness to execute, verified implementation, and any reserved developer completion
acceptance using the project's supported lifecycle. Explain dependency constraints and preferred order separately;
record the authorized batch and serial or parallel execution when specified. Do not invent record states or treat a
position in a task map as permission to begin work.

Ask a few consequential questions at a time, explaining trade-offs and recommending a direction. Record material
questions, the developer's answers, and resulting decisions concisely in the plan; distinguish confirmed answers from
agent recommendations, assumptions, and unanswered questions. Preserve important reasons when an answer changes.
Summarize rather than retain a transcript, and keep credentials out of the record.

Revise the plan as investigation, implementation experience, and new tasks change the understanding. Reconcile affected
steps, acceptance criteria, dependencies, and questions; do not merely append discoveries to an obsolete plan. Group
coherent work, using checklist steps or linked tasks according to independent scheduling and evidence needs. Distinguish
necessary discoveries within the authorized outcome from proposed scope expansion. Refer material unresolved choices to
the developer while continuing independent work; honor decisions and delegation already given.

Before implementing a major feature, obtain human approval of the concrete current plan. Make significant changes to
public behavior, interfaces, data, or architecture explicit. Record the actual approval and its scope; plan readiness,
agent review, and passing checks do not establish approval. Renew approval for material changes to that scope or its
constraints, while adapting ordinary steps within existing authorization. Preserve authorized small audit fixes and
refinement of the current implementation rather than treating every improvement as a new feature.

Report the current direction, important changes, and remaining questions with a link to the plan. Record readiness
honestly without manufacturing approval. A planning request does not itself authorize implementation, staging, commits,
or publication.
